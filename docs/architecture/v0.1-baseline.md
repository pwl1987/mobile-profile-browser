# V0.1 Architecture Baseline

**State: proposed baseline for implementation review.**

## 1. Product boundary

The product is an Android browser that manages multiple independent browsing Profiles on one device. V0.1 establishes the boundaries; it does not claim anti-detection completeness.

### In scope

- Profile CRUD and stable identifiers.
- Independent browser session/state per Profile.
- Profile activation/switching.
- Persistent Profile metadata.
- Network configuration abstraction.
- Device-profile schema.
- Security boundaries and test contracts.

### Out of scope for V0.1

- Full fingerprint spoofing.
- SSH implementation.
- Root-only traffic interception.
- Cloud synchronization.
- Remote control.
- Automated account creation or platform-specific evasion logic.

## 2. Profile boundary

Each Profile owns:

- browser/session data;
- cookies;
- localStorage / IndexedDB and equivalent site storage;
- cache where engine isolation permits it;
- permissions;
- bookmarks/history/settings that are explicitly Profile-scoped;
- device-profile reference;
- network-route reference.

Global app configuration must never be used as an implicit substitute for Profile state.

## 3. Runtime

Use WebLibre as the initial browser foundation. Its current repository is a Dart/Flutter workspace built around Gecko/GeckoView and already contains profile, isolation, and proxy-related functionality. Reuse should be preferred over duplicating mature browser primitives.

The first code-import milestone must record the exact upstream commit/tag used as the baseline.

## 4. Network layers

```text
Profile
  ↓
RouteSelector
  ↓
ProxyEndpoint
  ↓
(optional) SSH Tunnel
  ↓
(optional) TUN/VPN routing
  ↓
Internet
```

The Profile must refer to a logical route, not hard-code local ports. Tunnel lifecycle belongs to NetworkService.

## 5. Device profile

A device profile is a declarative configuration describing a coherent device/browser environment. It must have validation rules and compatibility metadata.

Examples of fields to model later:

- device family/model;
- Android version;
- browser/engine version compatibility;
- viewport/screen characteristics;
- DPR;
- touch capability;
- locale/language;
- timezone;
- hardware concurrency class;
- client-hints policy;
- WebGL capability class.

Values that the underlying engine cannot safely control must be marked **observed**, **derived**, or **unsupported**, rather than falsely reported as spoofed.

## 6. Data security

Sensitive values such as SSH private keys must never be stored in plain Profile JSON or logs. Credentials require Android Keystore-backed protection. Export must be encrypted by default.

## 7. Acceptance gates

V0.1 is not complete until:

1. two Profiles can be created and switched;
2. login/session state from Profile A cannot be observed in Profile B;
3. Profile deletion removes its scoped data according to the retention contract;
4. a crash during Profile switching cannot corrupt the active-profile registry;
5. device-profile validation rejects incompatible combinations;
6. no secret appears in logs, crash reports, or ordinary backups;
7. the exact upstream baseline is reproducible.
